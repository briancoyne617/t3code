# Personal fork: stable + dev

This fork of [pingdotgg/t3code](https://github.com/pingdotgg/t3code) runs two separate instances side by side:

- **Stable**: the build you use every day, where your real agents and threads live. It changes only through `fork promote`, `fork rollback`, or a manual `git` command.
- **Dev**: a separate checkout that agents edit. It has its own data and ports, so breaking it never affects stable.

Everything here runs inside WSL (Ubuntu). Open stable at **http://localhost:3773** in Firefox. Open dev at **http://127.0.0.1:5833**; it uses a different hostname so its login cookies stay separate from stable's.

## Layout

| Path                                | What                                                                                                                                                   |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `~/ide/t3code`                      | Main checkout, always on `custom`. Stable is built from it.                                                                                            |
| `~/ide/t3code-dev`                  | Dev worktree on `feat/*` branches. Add it as a project in stable.                                                                                      |
| `~/.t3-fork/releases/<time>-<sha>/` | One immutable build per promote. `src/` is the code with its own `node_modules`. `bin/node` is the Node it was built with. `web/` is the UI it serves. |
| `~/.t3-fork/current`                | Link to the release the stable server runs.                                                                                                            |
| `~/.t3-fork/client-current`         | Link to the UI stable serves. It can move without a server restart.                                                                                    |
| `~/.t3-fork/snapshots/`             | Copy of stable's database and settings, taken before each server swap.                                                                                 |
| `~/.t3-fork/state.json`             | What is deployed, plus a history of every promote and rollback.                                                                                        |
| `~/.t3-fork/logs/`                  | Logs of every command, plus `stable-server.log`.                                                                                                       |
| `~/.t3-fork/config.json`            | Paths, ports and limits (defaults in `fork/cli/lib/core.ts`).                                                                                          |
| `~/.t3-stable/`, `~/.t3-dev/`       | The two T3 homes. Each is only ever used by its own server.                                                                                            |

**Git branches.** `origin` is your fork and `upstream` is pingdotgg/t3code (push to upstream is disabled).

- `main` mirrors upstream; never commit to it.
- `custom` is the latest upstream stable tag plus your changes.
- Feature branches come off `custom`.

**Touching upstream's files.** The fork changes only two of them, and both are regenerated by code:

- `t3.json`: upstream's entries plus `fork/t3.fork.json`
- a marked block at the end of `AGENTS.md`

New features belong in new files with at most a one- or two-line hook into an upstream file. `fork/footprint.json` records each such hook and how big it is. See [AGENTS.md](AGENTS.md).

## Commands

Run `./fork/bin/fork <command>` in either checkout. The launcher always runs the copy in `~/ide/t3code`, so a half-edited dev copy can't break it. Set `T3_FORK_LOCAL_TOOLING=1` to run the copy you're editing. **Every command accepts `--dry-run`.**

| Command                                  | What it does                                                                                                                                                         |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fork status [--fetch]`                  | Shows what is deployed, health, running turns, the owner of each home, dev, and how far `custom` is behind upstream.                                                 |
| `fork dev`                               | Runs upstream's dev stack against `~/.t3-dev` and prints the URL. `--seed-from-stable` copies a read-only sample of stable's threads into dev (dev must be stopped). |
| `fork promote [branch]`                  | Merges the branch (default: the dev worktree's) into `custom`, builds, tests and deploys. See below.                                                                 |
| `fork promote --no-merge`                | Deploys `custom` as it is, e.g. after `sync-upstream`.                                                                                                               |
| `fork rollback`                          | Returns to the release before the current one. Run it again to step further back.                                                                                    |
| `fork sync-upstream [--to main\|vX.Y.Z]` | Merges upstream's latest stable tag (or main) into `custom`. Never deploys.                                                                                          |
| `fork setup`                             | One-time install; safe to re-run.                                                                                                                                    |
| `fork hooks [--check]`                   | Regenerates the fork's part of `t3.json` and `AGENTS.md`.                                                                                                            |
| `fork footprint [--write]`               | Checks, or records, how much the fork edits upstream-owned files.                                                                                                    |
| `t3 …`                                   | Upstream's CLI against stable (e.g. `t3 pair`, `t3 project add`). `update`, `service`, `uninstall` and `up` are refused.                                             |

The same actions appear as buttons: Dev, Fork: Promote, Fork: Rollback, Fork: Sync upstream, Fork: Status. They come from `t3.json`. In stable, open the dev project's actions menu (or Settings → Projects → Actions) and import them once.

### What promote does

1. **Merge.** Clones `~/ide/t3code` into a new release folder and merges the branch there. A conflict stops here and leaves `custom` untouched.
2. **Build and test.**
   - Runs `vp i`, then `vp run --filter t3 build`.
   - Checks the fork's hooks and footprint.
   - Runs `vp run check:changed` against the deployed commit. That's upstream's format, lint, typecheck and nearby-test check. `--full-tests` runs everything instead; `--skip-tests` skips it.
3. **Decide what changed.** Compares the build output with the deployed release:
   - the server bundle, plus the lockfile and Node version
   - the UI bundle
4. **UI only:** repoints `client-current`. The server keeps running and no agent is interrupted. Reload the tab.
5. **Server changed:**
   - Waits until stable has no running or waiting turns for 30 s (up to 30 min, `--timeout`). It ignores the thread the command itself runs in. `--force` skips the wait; restart continuation resumes cut turns.
   - Hands the swap to a separate systemd job (`t3-fork-swap-*`), so it survives the stable server and its terminals stopping.
   - That job: stops the server → checks nothing still owns `~/.t3-stable` → snapshots userdata → repoints `current` and `client-current` → starts the server → waits for it to be healthy.
   - Healthy means the new process wrote `server-runtime.json` after the restart, runs from the new release, and answers `/.well-known/t3/environment`.
   - If it isn't healthy, the job restores the previous release **and** the snapshot, and starts that again.
6. **Finish.** Fast-forwards `custom`, pushes it to your fork, and keeps the last 3 releases and snapshots.

### Rollback and your data

- If the database schema didn't change since the deploy you're undoing, rollback keeps today's data.
- If it did change, the old release needs the snapshot taken before that deploy. Restoring it **loses every thread and message since then**, so rollback asks first (`--yes` to confirm, `--keep-db` / `--restore-db` to choose).
- A safety snapshot of today's data is always taken first.
- Rollback doesn't change `custom`; revert the merge on a branch and promote if you want the change gone for good.

## Self-updates are off

| Upstream update path                             | Why it can't replace this fork                                                                                            |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| "Update server" / "Update everything" in the app | Only works when the server runs under upstream's launcher or the desktop app. Stable runs under `t3-fork-stable.service`. |
| `t3 update`, `t3 service install`                | The `t3` wrapper refuses them. Upstream's `t3` is not installed.                                                          |
| Desktop auto-updater                             | No desktop app is installed. A fork-built desktop app would have no update feed.                                          |
| Optional extra lock                              | `sudo install -m 644 fork/policy.json /etc/t3code/policy.json` makes every T3 Code server on this machine refuse updates. |

## Starting at boot

- `sudo loginctl enable-linger brian` starts your systemd user services at boot without a login.
- `t3-fork-wsl-keepalive.vbs` in your Windows Startup folder starts WSL at Windows logon and keeps it running.

Together they bring stable back after a reboot.

## Recovery

- **Stable won't start:**
  - Read `~/.t3-fork/logs/stable-server.log` and `systemctl --user status t3-fork-stable.service`.
  - `fork status` shows which release `current` points at.
  - `fork rollback`, or repoint by hand:
    ```sh
    systemctl --user stop t3-fork-stable.service
    ln -sfn ~/.t3-fork/releases/<older-id> ~/.t3-fork/current
    ln -sfn ~/.t3-fork/releases/<older-id>/web ~/.t3-fork/client-current
    systemctl --user start t3-fork-stable.service
    ```
- **Restore data by hand:** stop the service, then copy `~/.t3-fork/snapshots/<id>/userdata/*` over `~/.t3-stable/userdata/`. Remove `statev2.sqlite-wal` and `-shm` first. Then start it.
- **A promote or swap seems stuck:**
  - `fork status`
  - the newest file in `~/.t3-fork/logs/`
  - `systemctl --user list-units 't3-fork-swap-*'`
  - A leftover `~/.t3-fork/lock.json` whose PID is dead is ignored automatically.
- **Back to the official app if everything breaks:**
  1. `systemctl --user disable --now t3-fork-stable.service`
  2. Install the official desktop app (`winget install T3Tools.T3Code`), or run `npx t3@latest`.
  3. The official app uses `~/.t3`, so your fork data in `~/.t3-stable` stays untouched.
  4. To bring your threads along, start it once with `--base-dir ~/.t3-stable` (CLI), or copy `~/.t3-stable/userdata` to `~/.t3/userdata` first.
  5. Delete the Startup-folder `.vbs` if you no longer want WSL kept alive.
- **Undo the vp Node setup:** `vp env off node` (your shell goes back to nvm's Node); remove the `. "$HOME/.config/vite-plus/env"` line from `~/.bashrc` to remove vp entirely. The original is in `~/.bashrc.bak-before-vp`.
